= General-message authoring

`/admin/general` lets ITU editors and administrators prepare canonical issue-message drafts. The form uses generated ontology descriptions and the server validates the class selected by the existing corpus classifier. The message itself is the YAML envelope; register amendment wrappers and identifiers are not used. Optional ontology fields and opaque nested legacy objects survive round trips.

The API is Access guarded under `/api/admin/general-messages`. GET lists staff drafts; POST creates `{ob_issue_no,type,value}`. GET `/:id` reads a draft; POST `/:id` saves `{expected_revision,value}`. POST `/:id/approve` requires an ITU administrator and `{expected_revision}`. Approval snapshots exact YAML bytes for the approved revision. Subsequent edits clear approval and advance the optimistic revision, retaining the prior snapshot. A reserved publication request prevents further edits. Audit and state writes share a transaction.

`generalMessageArtifact(db,id,expectedRevision)` returns `{id,ob_issue_no,type,class_name,path,revision,content}` for the current approved revision. The publisher must reserve these exact bytes in `general_message_prs` before any external request, require administrator authorization, check the authoritative base repository for path collisions, and open a reviewed PR. It must not write directly to the default branch. Publication and merge evidence belong to the publisher integration, not this draft API.

New ordinary records receive `ob-issues/<issue>/<type>/<NNN>.yaml`; approved recommendations and running annexes use `general/approved_recommendations.yaml` and `general/running_annexes.yaml`. Sequence allocation is atomic within the draft database. Existing legacy Git files are not inventoried in D1: the publisher's base-repository collision check is required. POST `/import` opens an existing canonical record at its path through the configured repository reader. Approval proposes its replacement through review. Migration `0005_general_message_source.sql` retains imported source YAML independently of approval revisions; an unchanged form save and approval reuse those exact bytes. New drafts serialize normally. Large source, value and artifact fields use bounded gzip/base64 storage so the real telephone corpus fits D1 rows; API responses and publication artifacts always return decoded objects and exact YAML. Small database values stay plain. The storage codec bounds decoded fields to 32 MiB and encoded columns to 500 kB.

== Coverage and remaining gaps

Structured ontology fields are editable, including recommendation entries,
running-annex links, SANC country/code rows and notes, and nested telephone
country/area sections, contacts and dated communications. Scalar and multilingual
plain prose use textareas. Legacy rich-text objects remain read-only.
PR #124 owns the ontology changes for telephone communication contents,
multilingual custom titles, mid contents and SANC dispatch; they are not duplicated
here. Inline help explains the schema controls and draft/review workflow.

Opaque legacy objects remain preserved. A no-op load/save/approval retains the
complete original YAML, including comments, quoting, aliases and timestamps.
Edited drafts serialize new YAML after validation; original source is retained
so reverting the values restores the original bytes. Legacy singleton payloads
are preserved without conversion. The editor never authors ProseMirror documents.

Workerd/D1 checks and Node SQLite checks are reported separately in the PR delivery evidence.

exercise every record through import, form state, save, approval and artifact
read. The workerd/D1 suite exercises source retention with two representative
messages and real migrations. These local checks do not exercise remote GitHub
replacement PRs or a deployed editor.
