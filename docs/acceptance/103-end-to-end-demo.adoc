= Submission workflow: end-to-end acceptance demo (#103)

This executable demo drives the real Worker HTTP entry point, local D1 with the
real migrations, authentication, validation, review, GitHub publisher, composer,
notification outbox and queue consumer inside workerd. It demonstrates the
backend acceptance path for ituob/ituob.github.io#103. It is not evidence of a
live deployment or of rendered register changes.

== Run and reproduce

Use Node 22 or newer, installed dependencies, and a populated `data-ob` checkout.
The recorded run uses data pin `7d94b1c1a6425396525dc6e153ee09eece74cd54`.
The roster comes from committed `seeds/roster.sql`; the E.164 snapshot is served
in memory from dataset `1114-E.164D` at that pin.

[source,sh]
----
npm run test:worker -- test/e2e-submission-demo.test.ts
npm run test:worker
npm run typecheck:worker
----

The first demo test compares its transcript against the file below. The second
runs the complete scenario twice, cleaning D1 between runs, and requires equal
transcripts. To deliberately regenerate the transcript after reviewing a
behavior change, append `-u` to the focused test command. Normalization replaces
random submission identifiers, timestamps and the pin-selection digest (which
includes the submission identifier); it retains HTTP results, payloads, PR
repositories and branches, state transitions and recipient/subject evidence.

== What the scenario proves

. The operator bootstraps the first administrator directly in D1. Mock OIDC
  sign-in creates sessions; administrator provisioning grants the editor role.
  Admin requests independently require signed Cloudflare Access JWTs. A session
  cookie alone is refused, and the harness also verifies Access identity directly.
. Austria is activated; its delegate claims membership and an administrator
  verifies it. A verified Belgian delegate cannot propose Austria's entry.
. Adding the existing country code `43` produces stage2 warnings at
  `register_state` and `data.entries[0].country_code`. That draft is withdrawn.
  The correct `E164CCAmendment` MOD adds a multilingual-entry note; the snapshot
  freshness advisory remains. The editor requests changes, the member revises,
  and revision 1's bytes and hash remain unchanged.
. Approve opens an append-only patch PR on `ituob/itu-ob-data`, based on `main`.
  It writes `ob-issues/1351/e164-cc/001-MOD.yaml` on a submission branch.
  A simulated human merge and signed GitHub webhook move the item to `merged`.
. An administrator composes the edition and places the item. Stage opens a
  *site repository pin-bump PR into `staging`*, pinning the data repository's
  merged main commit. Stage waits for the second simulated human merge and a
  successful deployment of that exact staging merge commit. It publishes no item.
. Publish opens *one site repository `staging` -> `main` PR*. It waits for the
  third simulated human merge and successful production deployment of that exact
  merge commit. Only then does the edition and submission become `published`.
  Repeated pending calls do not create another promotion PR. Editors receive
  403 for Compose, Stage and Publish: those operations require an administrator.
. The audit hash chain verifies. Notification rows, recipients and recorded mail
  include review, approval, patch PR opening/merge and publication. The queue
  consumer delivers to the recording email provider, and all notification rows
  finish `sent`. Publication mail links to the discussion.

Thus Approve, Stage and Publish have different PR destinations and purposes.
There are *three human merges*, not an automatic merge or a direct protected
branch push. The fake GitHub log asserts that the Worker sends no merge, ref
update, PATCH, PUT or DELETE request.

== Boundaries and work not run

The in-memory GitHub REST model verifies the Worker's App JWT and models refs,
trees, commits, PRs, human merges and Actions deployment results. MockIdp serves
OIDC discovery, keys and token exchange locally; Access keys are generated by
the test. Outbound fetches are intercepted and unknown hosts fail. No request
reaches real GitHub, Cloudflare, an identity provider or an email service.
Email uses the durable local D1 recording provider.

The Ruby projection/replay step was *not run*. Applying the merged patch to
register projections requires `migrate_actions_to_changes.rb` and
`generate_register_snapshots.rb`, outside the Worker harness. The projection-gap
section of `../submission-workflow.adoc` describes the missing automation.
This demo proves that the patch's data pin reaches the modeled production
branch and that the Worker marks the item published; it does not prove replay
regenerated a register or that staging displays the changed note.

The staging/production site builds and real deploys were *not run*. Actions
success records are simulated. No full site build was requested. No browser/UI
exercise was run: requests use the Worker HTTP API and simulated browser cookies.
Live provider configuration, permissions, branch protection, real webhook
transport, real email delivery and visual/UI acceptance require separate
integration environments and credentials.
