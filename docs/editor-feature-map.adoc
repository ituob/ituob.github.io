[[task4]]
== Task 4: do textual datasets stay textareas?

*Yes for amendments, with four corrections to the issue text.*

* A textual dataset is edited through `TextAmendment`, whose payload is
  `dataset_code` plus `text` (a `String`) plus `position_on`, `notes` and
  `actions[]`. `SchemaNode.vue` renders a `String` leaf as a `<textarea rows="3">`,
  and `src/lib/form/ui.test.ts` asserts the payload `{ _class: 'TextAmendment', text }`
  with a two-paragraph value. So the text body is a plain textarea, as designed.
* The catalog marks seven publications `textual`, not five: rr251, bureaufax,
  coast-stations, list-v, list-viii, nnp, e212-icc (`src/lib/catalogs.ts`). The
  issue and Phase 4 list five. NNP also has typed entry classes, so it is
  reachable both ways; list-viii is textual because its typed class lacks
  `callsign` (`docs/draft-validation.adoc`). Update the issue text or the catalog.
* The textarea is ITU staff only. A member session submitting `TextAmendment` is
  refused (`worker/lib/submissions.ts:212`). A member state cannot amend a textual
  register through the web app; the legacy editor had no such restriction.
* The editor does not restrict the textarea to verbatim text: stage-2 checks only
  that the register is textual (`worker/lib/validation.ts:111`). Size and
  encoding limits are stated in `docs/submission-workflow.adoc:493` but were not
  traced to code here.

Related but separate: general-message prose (misc_communications, org_changes,
custom) is also a textarea where the ontology has a `String` attribute (D11-D13).
Where only a `Hash` exists (telephone communications, mid, custom title, sanc)
nothing is editable, which is the main blocker below.

== Blocks Electron retirement

Retirement needs "no remaining unique capability" (#101 acceptance). Ordered by
impact:

. *Telephone communication text (D7).* 377 of 396 legacy issues carry it; the
  field is read-only. Needs a plain-text attribute in the ontology plus form.
. *sanc (D15), mid (D18), custom title (D14).* Authoring is unavailable or
  read-only. Each needs a model fix or a recorded drop.
. *Editing and deleting existing general messages (D2, D3).* Only new drafts can
  be created; no replace-by-path, no delete.
. *Annex authoring (F1, F2).* No class and no form. Decide: add an annexes class
  and form, or retire `annexes.yaml` authoring and say so in #101.
. *Service-publication create/edit (G1).* Same kind of decision: a form, or a
  recorded "added in code" rule.
. *New-issue defaults (B8).* Authors, ISSN and languages are retyped per issue.
. *Bulk import / SEED (W2).* Required by #101, absent.
. *One amendment per publication per issue (E5).* No enforcement found.

Preconditions that are not features: #108 and #110 are open drafts, so every
IN PR row above is unshipped until both merge; identity provider, D1, GitHub App
and secret provisioning were not verified here.

Not blocking: calendar view (B6), author reorder (C6), help links (B10), amendment
header and `position_on` prefill (E4).

== Not run

* No test, typecheck, build or deploy was run for #108 or #110. Status comes from
  reading code on the two branch heads above; test counts quoted by those PRs'
  own docs were not re-run.
* The ITU translation service was not contacted; the PR's own doc says its live
  protocol was not observed.
* Whether newly authored general-message shapes render on the public site was not
  checked.
* The 21 legacy amendment targets were not individually matched to the 13
  structured and 7 textual catalog entries.

  6 mid, 88 custom, of 396 issues) were measured by grepping `issues/*/general.yaml`
  in a local `itu-ob-data` checkout at `e17484b`, which was not fetched from origin.
