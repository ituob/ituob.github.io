= Cloudflare bindings: what the Worker needs and how to provision it
:toc:

The live `wrangler.jsonc` (production) and `wrangler.staging.jsonc` retain the
static deployment configuration from main. They contain no D1, queue, or cron
bindings. Deploying them does not opt into resource provisioning. Without `DB`,
static assets and canonical redirects work; API and sign-in return an uncached
503 explaining the missing binding. Scheduled work skips with a diagnostic, and
queue deliveries retry rather than acknowledge messages. Without `NOTIFY_Q`,
outbox rows remain queued for later delivery.

`wrangler.bindings.example.jsonc` and
`wrangler.staging.bindings.example.jsonc` are *opt-in templates*, not selected by
CI. Their database IDs are placeholders and must never be deployed as-is. A dry
run verifies bundling only: it does not validate remote resources. Wrangler can
automatically create a missing queue before a subsequent D1 upload fails.

== What the opt-in examples declare

[cols="2,2,2,3"]
|===
| Binding / trigger | Production | Staging | Used by

| `DB` (D1) | `ituob-org-db` | `ituob-org-staging-db` | every route; `migrations/`
| `NOTIFY_Q` (queue producer) | `ituob-notify` | `ituob-notify-staging` | `flushOutbox` after a committed write
| queue consumer | `ituob-notify` | `ituob-notify-staging` | `queue` export, `worker/queue-consumer.ts` (max 5 retries)
| cron `*/5 * * * *` | yes | yes | `scheduled` export: outbox `sweep` (stale rows > 5 min) and `reconcile`
|===

Production and staging never share a database or queue.

== Owner steps (paid / account actions; not run by CI or agents)

[source,sh]
----
# Production
npx wrangler d1 create ituob-org-db           # copy database_id into wrangler.bindings.example.jsonc
npx wrangler queues create ituob-notify
npx wrangler d1 migrations apply ituob-org-db --remote -c wrangler.bindings.example.jsonc

# Staging
npx wrangler d1 create ituob-org-staging-db   # copy database_id into wrangler.staging.bindings.example.jsonc
npx wrangler queues create ituob-notify-staging
npx wrangler d1 migrations apply ituob-org-staging-db --remote -c wrangler.staging.bindings.example.jsonc
----

After creating each database, replace its placeholder `database_id`
(`00000000-0000-0000-0000-00000000000{0,1}`) in the corresponding example before
running the migration commands. Create the queues explicitly and apply all
migrations before enabling the webapp. Review identity and email settings below
before enabling consumers or the cron.

To opt in, copy the prepared resource sections into the corresponding live
config and commit that deliberate activation. CI continues using the live
configs; it never selects these examples. Update the checker’s live-config
policy in the same activation change after provisioning is verified. Keep
production and staging resources separate. The commands above are owner actions,
not steps performed by this change or its tests.

The country bootstrap and local-only `npm run seed:roster` command are described
in `roster-seed.adoc`, including future owner-only remote seed commands. The
bootstrap does not opt into live bindings or create resources.

== Deliberately not configured

* Identity: no `AUTH_MODE`, no stub, no `OIDC_*`. With `AUTH_MODE` unset the
  Worker fails closed (`test/stub-production.test.ts`). See
  `docs/identity-accounts.adoc` for the vars and the client secret.
* Email: no `EMAIL_*` keys. Set per `docs/email-configuration.adoc`; with no
  provider the consumer fails closed (`UnconfiguredEmailSender`), so notification
  rows are retried and nothing is sent. `EMAIL_PROVIDER=log` is the no-send mock.
* Secrets (`GITHUB_WEBHOOK_SECRET`, `OIDC_CLIENT_SECRET`, `EMAIL_API_KEY`) are set
  with `wrangler secret put`, never in these files.

== Guard

`npm run check:bindings` checks that live configs remain free of D1, queues and
cron triggers, and separately validates the opt-in examples against the Worker
`Env` contract and default-exported queue/scheduled handlers. It checks inherited
and aliased binding types, cross-environment resource isolation (including
consumers), and forbids secrets in plain vars. Valid JSONC comments and trailing
commas are supported. Placeholder IDs in examples are documentation only, not
proof of deployability.
