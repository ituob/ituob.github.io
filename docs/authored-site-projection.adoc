= Projecting authored amendments into site snapshots

The site checks out two independent, pinned inputs: `data` is
`ituob/itu-ob-data`, and `data-ob` is `ituob/service-publications-docs`.
Canonical authored amendments live under `data/ob-issues/`.
The historical corpus, register seeds, replay code and derived changes live in
the service checkout. Generating snapshots directly from its committed derived
changes does not include newly authored canonical amendments.

Run the projection from the site root, after installing the pinned service's
Ruby bundle with `BUNDLE_GEMFILE=ituob/Gemfile bundle install` in `data-ob`:

[source,sh]
----
python3 scripts/project-authored-data.py \
  --data-root data \
  --service-root data-ob \
  --data-ref "$(git -C data rev-parse HEAD)" \
  --service-ref "$(git -C data-ob rev-parse HEAD)" \
  --snapshots-out data/snapshots \
  --projection-root "${RUNNER_TEMP}/ituob-site-projection"
----

`--projection-root` must name a new directory outside both inputs and separate
from snapshot output. After successful checks it retains the complete service
overlay, including byte-exact authored issue content and derived changes.
Set `OB_DATA_ROOT` to its absolute path for subsequent Astro build/check steps;
the Astro configuration must use that environment variable for
`import.meta.env.OB_DATA_ROOT`. This makes issue pages and register pages consume
the same projection. The helper prints `OB_DATA_ROOT=...` but does not write CI
environment files. Keep the canonical data checkout available to other source
loaders. Local callers can use a fresh temporary path instead of `RUNNER_TEMP`.

Both refs must be full lowercase 40-character commit SHAs matching their
checkout HEADs. CI obtains them from the checked-out submodules, never a remote
branch. The helper does not fetch, checkout or update refs. It archives the
committed service tree into a temporary directory, ignoring uncommitted service
code. Python 3, Git, tar, Ruby and Bundler are required; the Ruby dependencies
are those of the pinned `data-ob/ituob/Gemfile` and lockfile. The helper sets
`BUNDLE_GEMFILE` to the temporary service's Gemfile and `SNAPSHOTS_OUT` to a
temporary output directory. Installed gems must remain available to Bundler
outside the original checkout (as with the existing CI bundle installation).

When `data` contains authored `ob-issues/` files, the pinned service must provide
`scripts/stage_authored_patches.py`, `scripts/migrate_actions_to_changes.rb`
and `scripts/generate_register_snapshots.rb`. Service commit
`fc626fc7110db64653f82e7c0c226fd8c38330d0` provides that contract; use that
commit or a reviewed descendant implementing the same interface.

The helper stages the entire cumulative authored tree using the service staging
helper with `base_ref = data_ref = data HEAD`. This is a projection of already
accepted history, not validation of a proposed data diff. The data acceptance
workflow remains responsible for immutable history across data revisions.
Staging preserves exact authored Git blob bytes and rejects collisions with
different historical bytes, malformed authored paths and missing metadata.
When the staging manifest contains general messages, the helper first runs the
pinned service's `validate-messages` command against that manifest and overlay.
This requires a service revision implementing general-message staging and model
validation; older revisions reject general-message paths during staging.
It then regenerates only derived register changes and snapshots from the
historical corpus plus authored overlay. It never calls `build_ob_issues.rb`,
rewrites canonical amendments, or derives patches from full register state.
The staging helper checks authored source and overlay hashes again after replay.
Generation failures, rescued per-register snapshot errors and byte changes all
fail the build; existing site output is retained until these checks pass.

If the pinned data tree has no `ob-issues/` entries, the helper reports
`historical-only` and generates snapshots from the service's committed derived
changes, preserving the existing baseline behavior. This does not claim any
accepted authored amendment or regenerate historical changes.

Focused regression checks use small real Git repositories, the service's real
staging helper, and Ruby fixture programs with standard-library dependencies:

[source,sh]
----
python3 -m unittest discover -s scripts/tests -p test_project_authored_data.py
----

The test suite reads the staging helper from committed `data-ob` HEAD.
For an alternate pinned service checkout, set `PROJECTION_SERVICE_ROOT`.
It checks cumulative input, exact bytes, historical preservation, exact refs,
missing trusted helpers, uncommitted service code, dirty canonical inputs,
projection failure, post-replay mutation and rescued generator errors. It does
not repeat the complete historical corpus build.
