# Printed labels and notes: validation

Part of [ituob/ituob.github.io#100](https://github.com/ituob/ituob.github.io/issues/100).

The attached evidence is generated by `test/generate_parity_evidence.rb`, which
runs the unchanged canonical `data-ob/scripts/parity_report.rb` and records every
classified Jekyll variant. Its only exclusions are the canonical auditor's two
existing documented cross-listed pages. The gate requires every other variant
to reach 95%; a better-scoring variant cannot hide a worse one.

- [Canonical report](parity_report.md): counts and worst-page results by type.
- [Canonical machine-readable report](parity_report.yaml): the minimum score for each local page.
- [Every Jekyll variant, CSV](parity_variants.csv): individual scores, verdicts, and exclusions.
- [Every Jekyll variant, JSON](parity_variants.json): the same scores plus source and HTML SHA-256 hashes.

The evidence regression spec checks that all four page types occur, each included
variant scores at least 95%, every canonical local-page score equals its actual
worst variant, the 429 expected local pages are present, and the source hashes
match the code being reviewed. It fails for missing reports, partial runs,
stale source, missing pages, or any below-threshold variant.

Provide checkouts/builds at those revisions using your own directories. No

The generator gives the canonical walker real temporary directories containing
read-only links to the reference files. It displays the portable logical roots
`reference` and `build`. It retains the canonical token, coverage, exclusion,
and worst-variant rules; a cached normalized-link membership test avoids
repeating the auditor's identical link normalization for each candidate.
The process fails rather than reporting success for an empty reference tree.

## Separate decisions on the extra changes

### Incomplete-data banner: retained

The existing component defaults its `incomplete` prop to false. The issue page
now passes the loader's flag explicitly. Preview checks and regression specs
compare the real metadata with the rendered notice:

| Issue | Data marks incomplete | Notice expected |
| --- | --- | --- |
| 669 | yes | present |
| 955 | no | absent |
| 1125 | no | absent |
| 1296 | no | absent |
| 1343 | no | absent |

This prop correction does not change the loader's existing completeness
classification. In particular, the legacy marker in issue 1075 coexists with
populated message data; the loader already classifies that issue as complete.
That pre-existing classification is not changed by this patch.

### Annex chronology: removed

The official [OB 1283 English PDF, printed page 3](https://www.itu.int/dms_pub/itu-t/opb/sp/T-SP-OB.1283-2024-OAS-PDF-E.pdf)
lists E.118 at OB 1283 (position 31 December 2023) and E.212 at OB 1280
(position 15 November 2023). The earlier
[OB 1161 English PDF, printed page 3](https://www.itu.int/dms_pub/itu-t/opb/sp/T-SP-OB.1161-2018-OAS-PDF-E.pdf)
lists E.118 at OB 1161 (position 1 December 2018). Thus the printed numbers use
the latest annex for both publications.

However, there is no current corpus event without `position_on` to confirm the
proposed carry-forward rule. Also, E.212's stored `2023-11-14T23:00:00.000Z`
renders as 14.XI.2023 in the current UTC formatter, while the printed date is
15 November. Following the maintainer's instruction, the chronology change and
its dedicated tests are removed in full. `src/lib/loaders.ts` matches main.
The [follow-up issue draft](annex-follow-up.md) contains the printed evidence and
acceptance checks. The lane's `gh` guard requires Cortex or a person to create
that issue; the task agent could not post it.
